# Reviewed pre-resume recovery

This explicit route supports one narrow failure: a first cold-adoption attempt
has a preserved RECONCILIATION_REQUIRED SID journal with no resume/work marker,
and its exact launch stopped at `transfer_reconciliation_not_bound` before
provider mutation, while its original status remains UNKNOWN and trace STOPPED.
A provisional transport and catalog read are real effects;
they are never relabeled as no effects. Other failures and ambiguous provider
effects remain UNKNOWN and blocked. No API here stops a worker or resets state.

`screen_pre_resume.reconcile_pre_resume(home, plan, owning_guard=guard)` publishes
one create-only disposition. `plan` uses schema `agentos.pre-resume-request/v1`:

- `session_id`, raw `failed_adoption_sha256` and `failed_launch_sha256` select the
  canonical original SID journal and exact launch journal.
- `failed_adoption` is the exact original adoption input, including its existing
  pending reconciliation ref. The original old worker's evidence/effects remain
  independently reviewed, not replayed.
- `failed_worker_name`, `describe_operation_id`, `worker_pins` bind exactly
  identity.json, bootstrap.json, state.json, request.json and the single
  responses/OPERATION_ID.json in the provisional worker.
- `dispatch_binding` contains exact `session_id`, `turn_id`, `task_id` of the
  failed caller's workflow. These are qualified caller metadata, not guessed
  native IDs. Its canonical dispatch claim path must currently be absent at
  disposition publication and replacement reservation.
- `no_native_evidence: {path, sha256}` pins independently qualified normalized
  evidence, described below. `replacement_name` and `replacement_request` bind
  one exact proposed continuation.

JSON inputs/receipts are bounded to 128 KiB; selected regular non-symlink source
files also have that bound. The core checks operation/worker/connection/request/
bootstrap/attempt consistency, the original before_transport binding, STOPPED
and false mutation/resume/work markers, READY with an explicitly null session,
exact successful describe_adoption response equal to launch preflight and no
extra mailbox responses. Existing startup, rejected-startup, pending or launch
files in that provisional worker refuse. Those checks alone prove no native
effect only under the trusted execution/trace and owner review below.

The evidence schema is `agentos.pre-resume-evidence/v1`, with exact SID,
attempt/request/worker/connection bindings, `coverage: COMPLETE`, integer zero
`native_resume_count`, `native_probe_count`, `native_work_count`, actual canonical
`claim_path`, `claim_state: ABSENT`, `dispatch_binding_sha256`, qualified
`source_refs` and `execution_code_pins` for screen_launch.py, codex_launch.py,
screen_adoption.py and session_launch.py. File hashes do not prove what a past
process loaded. The actual owning accessor must verify its execution identity,
complete native trace, absence of native resume/probe/work and claim boundary
against exact original sources. Missing provenance refuses; caller flags or a
null session alone cannot supply it.

`guard(plan)` is an existing trusted context manager holding current controller
exclusion. It yields a fresh `check(query)`. The query binds
`phase: review_pre_resume`, plan/failed-adoption/no-native-evidence hashes, SID and
replacement request digest. The result echoes every binding and carries
`observed_at` within 60 seconds, nonempty `reviewer`, `evidence_ref` and
`owner_exclusion_token`, and true values for `owner_exclusion_held`,
`old_and_provisional_lineage_absent`, `execution_identity_and_trace_verified`,
`no_native_resume_probe_work_verified`, `claim_absence_verified`,
`transport_effects_reviewed`, `same_canonical_owner_continuation_verified` and
`historical_transfer_preserved_not_accepted`. These are factual qualified
readbacks/review, not authority generated by this module.

Both the original old worker and failed provisional worker must be actually
quiescent, with lifecycle worker.lock removed normally. No automatic stale-lock
cleanup is provided. All pinned inputs and claim absence are rechecked after
the held guard. Publication uses the existing SID lock and never changes an old
SID/launch/mailbox record. Source fixtures grant no stop, security disposition,
fencing or recovery authority.

The exact replacement must retain the failed request's semantics, settings,
goal/context/authority and target inventory. Its only allowed changes are a
fresh launch ID and omission of the incorrectly active historical top-level
transfer. Root must independently verify that this is actual same canonical
owner continuation, with no current transfer effect intended. The historical
request/transfer remains preserved and unaccepted. This route never edits a
request or waives `_targets`: any active transfer still needs its ordinary
proofs. A new destination registry name is mandatory.

The returned `{failed_adoption_sha256, receipt_sha256}` selects the canonical
immutable receipt at `state/screen-adoption-pre-resume/SID/FAILED_SHA.receipt.json`.
Add it as `adoption.pre_resume_recovery`. One create-only child attempt at
`FAILED_SHA.attempt.json` consumes it under the same SID lock. Fresh adoption
guards additionally bind `pre_resume_binding_sha256` to the supplied derived
`pre_resume_binding`, and verify `pre_resume_no_native_effects_verified`,
`same_canonical_owner_continuation_verified` and
`historical_transfer_preserved_not_accepted`. Normal current ownership, security,
target, catalog/startup/settings/probe and dispatch gates remain mandatory.
Old no-claim evidence is historical after the legitimate new dispatch claim;
the current guard must distinguish the new claim instead of asserting current
absence forever. Neither failed/reserved child nor a new name/ID permits replay.

After this child actually succeeds, later successful-successor admission may
explicitly carry the same ref as `pre_resume_history` alongside the ordinary
`successor` tip hash. Only that verified historical entry can precede the
successful chain; the original failed root is never accepted as success. Existing
rc2050 success behavior and all other UNKNOWN/in-flight refusals stay unchanged.
There is no generic failed-attempt retry path. Actual installation and recovery
require separate root acceptance. Storage is cooperative and not an adversarial
same-UID or crash-proof multi-file transaction boundary.
