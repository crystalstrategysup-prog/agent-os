# agentos-implementation-control

Use **Solution integrity** and **Project development** from `agentos workflow
guidance`, reusing the current body from entry. Build the connected result of the current level before recursively
refining a selected part. Preserve the owner's scoped development level (default
3 of 5), explicit stubs, module boundaries and diagnostic/error-log requirements.
The canonical PROCESS defines the level scale and sufficient stage checks.

When diagnostic level 0 is active, continue **Project diagnostics** from
`agentos workflow guidance --method project-diagnostics` or the same PROCESS.
Use it before substantial work with material unknowns, and review its need at
major milestones against changed evidence. Preserve the selected 1–5 level;
record the current dossier, consequential gaps and next action, then return to
that mode, honoring a newer explicit owner choice. Do not turn every increment
into a full audit or require all findings to be fixed before independent work.
This diagnosis grants no readiness or additional effects.

For a concrete malfunction needing causal investigation, read **Causal debugging**
from `agentos workflow guidance --method causal-debugging`, or
read **Solution integrity** and the selected method in `resources/docs/PROCESS.md` if the CLI is unavailable
(locate installed resources with `agentos resources`). Continue the existing
journal and evidence; return to the development plan after sufficient repair or
an explicitly scoped mitigation. Ordinary features need no artificial failure.

Check that the project gate passes for the exact task. Read the stage contract,
write paths, authority, and approved checks. Implement a complete change within
that contract with checks appropriate to the selected level and concrete risks.
Stop when its criteria and required checks are satisfied; a declared early stage
may finish with a working scaffold or explicit stub. Do not
weaken a required protection to make it pass. If scope expands, checkpoint the
task, update the scope and documents, and enter again. Verify source rather than
relying on an external report.

Select bounded relevant sections before reading large files. Source reads can
use `agent_os.source_sections` to refuse oversized rendered output
before printing any source; see `docs/OBSERVED_EVIDENCE.md`. Reuse supplied exact
references before discovering replacements. For primary command proof isolate
the business command: a later successful read must not mask an earlier exit.
Ordinary source dependencies needed for the same authorized goal are routine discovery, not a
new permission gate. A newly discovered protected effect still needs its own
authority. When an observation is refused, stop dependent business work, but
finish mandatory cleanup and reconciliation of resources already owned by the
task; refusal does not cancel those obligations or authorize unrelated cleanup.

When the owner explicitly requests supervised forks, pass the next task's delta
and reuse accepted facts with their scope and freshness limits. Do not rebuild
the whole handoff or fork for each helper. Otherwise keep the existing executor.
For an already READY task, use assess to check current evidence; do not repeat
ready unless the workflow requires a new readiness transition.

Before an external write, verify the target host, current source and runtime,
authority, and rollback. Local task permission does not authorize another
production system. Output changed source, tests, docs, and actual limitations;
then run verification and closeout.

The installed `resources/docs/PROCESS.md` and README are normative; locate them with
`agentos resources`. Project gates apply to real changes. Reading requires no
intake or observation. Native hooks remain excluded and must not be enabled or
restored. Neither CLI output nor profile text grants external authority.

Indexed results successor: follow `resources/docs/INDEXED_HANDOFF.md`. Both coordinators and workers query the selected owner library for prior results, then verify ID/revision/evidence and freshness before summarizing. New/resumed terminal transitions require accepted searchable handoff; a checkpoint stays unfinished. Historical permissions and archived instructions grant no new authority. Physical session cleanup is not implemented. Source instructions do not prove live coordinator adoption.

For work coordination read the single `resources/docs/COORDINATOR_KNOWLEDGE_INDEX.json` then selected `resources/docs/WORK_COORDINATION.md` references. Keep parent open until checked original user result. Every partial/final report needs verification, remainder and next owned action; receipt or session completion is not user-goal acceptance. Preserve independent work and reconcile exact unknown operations before retries. Personal role/name knowledge stays in the selected private overlay; linked files require explicit read/hash checks and live root/voice adoption is separate.

For completion-enabled coordination, read `docs/COMPLETION.md`. Preserve the original goal and unfinished work through a turn or handoff. Require current exact receiver ACK and protected ownership transition; unknown effect outcomes require reconciliation before retry. A local stage checkpoint or completed chat cannot accept the parent project.
