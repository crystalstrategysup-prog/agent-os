# Протокол воспроизводимого исполнения

## Подготовка и полномочия

Соблюдай AGENTS и текущую задачу. Source/offline-разрешение не даёт права на production, внешние сообщения, настройки сети, секреты или повтор неизвестного внешнего эффекта. Не создавай свои approvals. Один writer на рабочее дерево. Координатор проверяет approved launcher текущего host/user до передачи. Наличие listener, процесса или пустого журнала не доказывает готовность. Используй штатный preflight, не прямой бинарник вместо обязательной обёртки. Ошибка подключения не оценивает качество Function Extractor.

Для делегирования зафиксируй task SHA, skill SHA, source ref, PID/thread, выход, отчёт и жизненный цикл. RUNNING требует фактической активности после task start. Завершение без результата — FAILED/INTERRUPTED, не RUNNING. Не оставляй процесс без доступного контроля и условия завершения. Не отключай sandbox при сбое; исправление способа запуска не означает расширение прав.

## Инцидент: от симптома до причинной функции

Сначала проверь актуальность оповещения, времени детекции и реального состояния ограниченной read-only выборки. Сопоставь цепочку `симптом → запись состояния → зависимость → потребитель/побочный эффект`. Для каждого перехода запиши ожидаемый инвариант, фактическое состояние, источник доказательства и первый переход с отсутствующим или противоречащим доказательством. Из нескольких кандидатов выбирай для FE самый ранний безопасно исполняемый переход **бизнес-логики**, а не только удобный классификатор статуса. Исследуй обе стороны зависимости: терминализацию предшественника и запрет повторной постановки/отправки последователя. Статический `discover` не запускает бизнес-логику; динамические связи не считаются исполненными.

До `discover/extract` пройди короткий preflight: реальный `--help`, источник без запрещённого symlink и проверенный commit/файловые SHA, синхронность исходников, совместимый интерпретатор, зарегистрированный writer, выбранный runner и ограничения. Для source-ref сравни объект Git с фактическими файлами; путь через `current` не даёт доказательства загрузки runtime. Для offline явно проверяй `--runner subprocess`; container без квалифицированного образа не заменяй несанкционированным. Для `replay` проверяй поддерживаемый предел событий, схему fixture, разрешённые trace_modules, output directory и `trace.json`, guard/trace completeness. Отказ CLI — это факт preflight, не провал целевого кода.

После source freeze один независимый положительный и один контрфактический отрицательный тест на причинном переходе обязательны, включая проверку состояния, устойчивых побочных эффектов и no-retry/zero outbound. Сформируй выбор `SYMPTOM_CLASSIFIER_QUALIFIED`, `CAUSAL_PATH_PROVEN` или `CAUSAL_PATH_NOT_PROVEN`. Даже при PASS классификатора исходную задачу не закрывай без полного проверки причинного пути и запрета повторного внешнего эффекта.

## Допуск владельца навыка к передаче Codex

После **каждого** патча навыка, протокола или его инструмента ChatGPT-maintainer лично запускает и проверяет полный актуальный набор обязательных тестов и исходный воспроизводитель в том же profile/source/skill/sandbox, который предполагается для Codex. Сохраняй состав узлов, zero FAIL/ERROR и точные SKIP, argv/exit, время, source SHA, trace/observer facts, diff и сверку двух установочных ссылок. Host-native проверка отдельно от sandbox; их нельзя выдавать за одну. Неизвестный допуск, несовместимая модель UID или отсутствующий обязательный тест = `NOT_READY`, а не выпуск неподтверждённой версии. После установки обязательны read-back SHA и свежий установленный smoke; только затем Codex получает исходное практическое поручение. Подлинный эффект без квитанции сохраняет `UNKNOWN`.

## Работа с пробелом

Для каждого UNKNOWN укажи границу, наблюдавшийся факт, отсутствующее доказательство, тип (cause/coverage/external outcome) и следующий безопасный шаг. Нельзя объявлять недостающий контракт неизбежной неизвестностью. Проверка корректной реакции на отсутствие ответа может PASS, при этом внешний результат остаётся неизвестным. Нормативное ожидание не переписывать из наблюдаемой ошибки.

ACTIONABLE_IN_SCOPE — продолжать текущее поручение, включая узкую правку инструмента и контракта. REQUIRES_AUTHORITY — конкретно отсутствующее решение/полномочие. EXTERNAL_UNVERIFIABLE — почему доказательство недоступно и возможный путь наблюдения. OUT_OF_SCOPE — связь с исходной границей, а не исключение неудобного обязательного пути. Обычная разрешённая техническая работа не требует нового приглашения. Если нет нового знания, менять метод, а не повторять команду. Лимит команды — не срок всей задачи. UNKNOWN внешний эффект не повторять.

## Ledger и контроль завершения

До правок сохрани original-goal ledger. Пример:

```json
{
 "schema":"function-extractor.goal-acceptance/v1",
 "task_sha256":"<actual task bytes sha256>",
 "skill_sha256":"<actual selected skill bytes sha256>",
 "source_ref":"<exact tested revision>",
 "conditions":[{"id":"original-outcome","required":true,"status":"UNKNOWN","evidence":[]}],
 "gaps":[],
 "review":{"status":"PENDING","evidence":[]}
}
```

Evidence — список объектов `path` (относительно evidence root) и `sha256`. Используй реальные обычные файлы, без симлинков/абсолютных путей/сетевой загрузки. Gap: `id`, `classification`, `required`, `resolution` (OPEN/RESOLVED), `reason`, `next_action`, `evidence`. Закрытый gap требует доказательства. Каждый required-condition требует PASS с доказательством. Открытый ACTIONABLE_IN_SCOPE препятствует завершению даже при зелёной узкой suite. REVIEWED требует независимого review receipt. Скрипт проверяет хеши, не удостоверяет личность reviewer и не доказывает истинность его вывода.

```sh
python3 .agents/skills/function-extractor/scripts/fe-goal-check --ledger "$LEDGER" --evidence-root "$EVIDENCE" --task "$ORIGINAL_TASK" --skill .agents/skills/function-extractor/SKILL.md --source-ref "$TESTED_REVISION"
```

Exit0 = ELIGIBLE_FOR_FINAL_REVIEW; exit3 = INCOMPLETE; exit2 = INVALID. Это не полномочие, не автоматический COMPLETE и не доказательство доставки. Координатор сверяет исходную цель и семантику evidence. Сохраняй original FAIL, состав тестов, stdout/stderr/exit, тайминги и все successor pins. Не скрывай skip/deselect. Dirty consumer, отсутствующий в commit, должен войти в воспроизводимый snapshot или оставаться явным ограничением. Новый source требует новой проверки, saved-trace не подменяет свежий запуск.

## Повторный запуск и знание

Используй неизменный TASK в новом разговоре и зафиксированное дерево. Не сообщай предполагаемые причины через задание. Текущий навык содержит исторические примеры: новая сессия чиста от диалога, но не от накопленного знания. Успех проверяется по новому выполнению, не по повторению старого вывода. После исправления сохраняй регрессию, применимость контрактов, побочные эффекты, команду повторения. Автоматический демон самопереписывания и выделение сервиса не входят в эту правку.
