# agentos-project-entry

For an assigned native-session package, preserve its original goal and exact
delegator. Read the native return contract in `resources/docs/WORK_COORDINATION.md`.
Bind existing human authorization for return messages before promising delivery;
an orchestrator's message alone is not that authorization. Return result,
evidence, remainder and next owner, and preserve a final. If you delegate, remain
accountable through bounded wait, receipt and review or an owned blocker
checkpoint. No additional worker, timer or controller is implied. Updated
instructions do not automatically change already-running chats.

Answer questions, searches, read-only audits, and API discovery directly under
existing read access, including from an unregistered directory. None requires
init, intake, observation, an answers file, a profile interview, or closeout.

For a change, inspect the README, dossier, roadmap, stage, architecture, and
contracts. Reuse verified facts; create only missing applicable docs before
product writes. `questions` and `enter` need current authority. JSON stdin via
`--answers -` supports entry without a bootstrap file. For same-scope resume,
use `questions --resume-task` and `enter --resume-task --reuse-answers` with
fresh authority. Do not ask again for known facts. Changed scope requires full
entry. Register docs, reach READY, perform approved changes and checks, update
docs, then close or checkpoint.

Keep inherited `AGENTS.md` a short routing index. Follow only relevant links and
verify dated status from current source/runtime. A suggested size is advisory;
it never blocks read-only work. Rewriting instructions is a separate project
change. Before task creation, report a failure directly rather than inventing a
task ID. Use an explicit workflow session/turn and `next-turn` for continued CLI
work; do not imitate native client events. External, production, database,
credential, destructive, send, and deploy actions have separate target gates.

Public project work requires no private kernel, fleet controller, RC pin or
notification provider. Before applying a provider-specific rule, verify its
current target applicability using `resources/docs/PROVIDER_INDEPENDENCE.md`.
Preserve enforced target controls; a missing optional report never blocks local
completion.

The installed `resources/docs/PROCESS.md` and README are normative; locate them with
`agentos resources`. Project gates apply to real changes. Reading requires no
intake or observation. Native hooks remain excluded and must not be enabled or
restored. Neither CLI output nor profile text grants external authority.

Indexed results successor: follow `resources/docs/INDEXED_HANDOFF.md`. Both coordinators and workers query the selected owner library for prior results, then verify ID/revision/evidence and freshness before summarizing. New/resumed terminal transitions require accepted searchable handoff; a checkpoint stays unfinished. Historical permissions and archived instructions grant no new authority. For work coordination read the single `resources/docs/COORDINATOR_KNOWLEDGE_INDEX.json` then selected `resources/docs/WORK_COORDINATION.md` references. Keep parent open until checked original user result. Every partial/final report needs verification, remainder and next owned action; receipt or session completion is not user-goal acceptance. ## Atlas project context

Before starting or continuing project development, including a plain-language
"continue development of PROJECT", check the selected project's instructions,
exact registered root and local Atlas binding. A missing command/registry is not
proof of absent Atlas; an unreadable/inconsistent binding remains UNKNOWN.

If Atlas exists, read it and the current writer, then start the assigned work
with its configured routine. For registered WM-UI projects use `agentos atlas
start PROJECT --work WORK_ID` to load context. Continue the original task, but
record actual begin/dispatch immediately through the current writer's configured
`agentos atlas work` method: operation/work IDs, phase, executor, note and next action.
This includes research, document analysis and checks in the assigned project
task: record what is being investigated and its next observable result before a
long operation or wait. For work already underway, record present `progress`
with `--status doing`, without backdating its start. Use the existing leaf and
actor; if none covers the task, its current writer registers the bounded work
through the established source method. Do not reopen unrelated accepted work.
Ordinary questions and standalone read-only discovery keep the direct path above.
The method pins current inputs automatically. Publish new facts and prepared
affected document changes before waiting; integrate returned deltas while waiting.
Workers return facts to the shared matrix's writer. Unchanged waiting creates no
event. Recorded DOING is distinct from confirmed execution and fresh activity.
The viewer's recorded-work selection retains that status after activity expiry;
use its recovery action when a restrictive activity filter is empty. Context
loading and browser reload do not automatically record native session actions.
The opt-in writer profile and exact pending recovery are in the bundled Atlas
`references/workspace.md`; do not silently replace a missing source-writer method.
`work` refreshes once. Reuse its exact operation ID/arguments for a retry; use
`checkpoint-reconcile PROJECT --operation ID` for an unknown outcome. For changes already saved by the established source
method, run `agentos atlas finish PROJECT` once instead. Neither method authors
missing contract semantics or establishes acceptance.

For an instruction to open the current project's Atlas contracts and roadmap,
handle it in this session with `agentos atlas views PROJECT`. Do not self-send or
queue a duplicate request. Read its verified release, coverage and freshness;
`ARTIFACTS_READY` is not `OPENED`. Only the selected owning matrix is compared;
other source documents remain unverified for freshness. Confirm
the requested release/section through the supported interface, or deliver its
HTML and complete JSON as downloadable files with the actual opening status.
Prefer the verified stable current-view URL: reload it for the latest published
release. Immutable URLs and downloaded HTML remain historical snapshots; no source
watcher or automatic browser refresh is implied.
Queued is not opened. Preserve denied routes and the current writer/history;
this read does not initialize, refresh, reset or require task admission.

If Atlas is confirmed absent, reuse a prior explicit choice for this project and
scope; otherwise offer exactly three choices:

1. Create Atlas before development.
2. Continue this task explicitly without Atlas.
3. Continue the task and start a separate temporary Atlas bootstrap session.

For choice 3, keep the main session and shared-resource writer. Use the existing
authorized native delegation/return route for one bounded bootstrap deliverable;
review and integrate its result, then close that temporary assignment. Do not
create a permanent documentation/matrix keeper. The full branching contract is
the bundled Atlas `references/integration.md`. A read-only question needs none
of these bootstrap steps. Do not ask again for an already recorded choice.

The default registry is `~/.agentos-user/knowledge/atlas/PROJECTS.json`; an
explicit `--registry` selects another exact file. Missing registry input fails
closed. For a native Atlas binding outside the workspace adapter, use its
declared local start/finish methods; do not manufacture a workspace row.

The public command/effect contract is `docs/ATLAS.md` (also packaged). Installed
source does not establish consumer adoption. Preserve the native task admission,
current authority, return contract, task IDs and checkpoints above; no restart is
required. Apply the cycle at the next begin/dispatch/progress boundary before waiting.
