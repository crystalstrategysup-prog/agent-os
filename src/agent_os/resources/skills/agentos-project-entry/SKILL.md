# agentos-project-entry

Answer questions, searches, read-only audits, and API discovery directly under
existing read access, including from an unregistered directory. None requires
init, intake, observation, an answers file, a profile interview, or closeout.

For a change, inspect the README, dossier, roadmap, stage, architecture, and
contracts. Reuse verified facts; create only missing applicable docs before
product writes. `questions` and `enter` need current authority. JSON stdin via
`--answers -` supports entry without a bootstrap file. For same-scope resume,
use `questions --resume-task` and `enter --resume-task --reuse-answers` with
fresh authority. Do not ask again for known facts. Changed scope requires full
entry. Register docs, reach READY, perform approved changes and checks, update
docs, then close or checkpoint.

Keep inherited `AGENTS.md` a short routing index. Follow only relevant links and
verify dated status from current source/runtime. A suggested size is advisory;
it never blocks read-only work. Rewriting instructions is a separate project
change. Before task creation, report a failure directly rather than inventing a
task ID. Use an explicit workflow session/turn and `next-turn` for continued CLI
work; do not imitate native client events. External, production, database,
credential, destructive, send, and deploy actions have separate target gates.

Public project work requires no private kernel, fleet controller, RC pin or
notification provider. Before applying a provider-specific rule, verify its
current target applicability using `resources/docs/PROVIDER_INDEPENDENCE.md`.
Preserve enforced target controls; a missing optional report never blocks local
completion.

The installed `resources/docs/PROCESS.md` and README are normative; locate them with
`agentos resources`. Project gates apply to real changes. Reading requires no
intake or observation. Native hooks remain excluded and must not be enabled or
restored. Neither CLI output nor profile text grants external authority.
